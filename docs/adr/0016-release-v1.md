# ADR 0016. Выпуск v1.0: проверки перед выпуском

**Статус:** принято. **Дата:** 2026-09-28. **Этап:** P17.

## Контекст
P17 требует проверить выпуск с нуля на Windows и Linux, выдержать 10 одновременных кандидатов (ответ на «Запустить» до 10 с в 95 % случаев при `RUNNER_CONCURRENCY=4`), пройти чек-лист безопасности и выпустить тег v1.0.0.

## Решения
| Вопрос | Решение | Обоснование |
|---|---|---|
| Проверка с нуля на Linux | E2E-задание CI поднимает стек через `scripts/up.sh` на чистой машине GitHub (сам создаёт `.env` из примера, собирает песочницу и образы) | Это ровно быстрый старт README; проверяется на каждом pull request, а не один раз руками |
| Проверка с нуля на Windows | Руками перед выпуском: свежий клон с GitHub, свой `.env`, `scripts/up.ps1`, E2E и `demo-seed` на нём (результат — в [security-checklist.md](../security-checklist.md)). Второй стек рядом с рабочим — через `COMPOSE_PROJECT_NAME` (своя база) | Windows-машины в CI нет; Docker Desktop на WSL2 — основной вариант показа |
| Длинные пути на Windows | Файлы банка задач не переименовываются; README велит клонировать в короткий путь или включить `core.longpaths` | Самый длинный путь — 140 символов; клон в папку с путём длиннее ~115 символов не создаёт файлы (MAX_PATH 260). Переименование пакетов задач потребовало бы перепроверки всего банка |
| `scripts/up.*` | `docker compose up --build -d --wait`: скрипт возвращается и печатает адрес, когда сервисы здоровы | Раньше адрес печатался, пока web и runner ещё запускались |
| Нагрузочная проверка | Свой скрипт на Node.js ([e2e/load/run-load.mjs](../../e2e/load/run-load.mjs)) через API кандидата, без k6 и браузеров; измеряет путь «POST run → результат» и отдельно время песочницы; сессии завершаются после последнего замера. Методика и результаты — [performance.md](../performance.md) | Узкое место — песочница и очередь runner, а не отрисовка страницы: 10 браузеров мешали бы замеру на той же машине; k6 — ещё одна установка, а Node.js уже нужен для E2E |
| Очередь runner | Остаётся FIFO: запуски и отправки в одной очереди | Требование выполнено (p95 7,6 с); приоритет запускам над отправками — изменение поведения перед выпуском без необходимости |
| Проверка зависимостей | `npm audit` (frontend, e2e) и Trivy по собранным образам (`gits-api`, `gits-runner`, `gits-web`, `gits-sandbox-java`): Java-библиотеки внутри jar и пакеты ОС. В CI — Trivy (версия закреплена) по образам с `--severity CRITICAL --ignore-unfixed --exit-code 1` и `npm audit --audit-level=critical` | OWASP dependency-check без ключа NVD API скачивает базу часами; Trivy смотрит то, что реально попадает в образ. Критичные уязвимости без исправления не блокируют CI — их нечем исправить |
| Токены приглашений в логах | nginx пишет журнал доступа в своём формате: `/c/<токен>` (от 20 символов) заменяется на `/c/***`, и в запросе, и в Referer; CI проверяет, что после E2E в логах всех сервисов нет токенов | Токен — ключ входа кандидата; журнал nginx по умолчанию хранил его в каждой строке, где страница кандидата грузила скрипты |
| Тег и релиз | Тег `v1.0.0` на коммите `main` после вливания P17, GitHub Release с текстом из `CHANGELOG.md` | Тег указывает на проверенный CI коммит |

## Последствия
- Новая критичная уязвимость в зависимости или базовом образе с доступным исправлением роняет CI до обновления — это и есть назначение проверки.
- При изменении формата токена приглашения (длина, алфавит) нужно обновить регулярные выражения в `frontend/nginx.conf` и шаг CI.
- Цифры производительности сняты на одной машине (ноутбук, 8 потоков); на другой машине их нужно перемерить тем же скриптом.

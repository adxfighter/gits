# Лимит заявок перевозчика

Маркетплейс передаёт заявки на забор груза в API перевозчиков. У каждого перевозчика (ключ — `carrierId`) свой лимит: ведро `CarrierBucket` ёмкостью `capacity`, которое пополняется со скоростью `tokensPerSecond`. Заявка на `n` мест требует `n` разрешений.

`CarrierOrderLimiter`:
- `tryAcquire(carrierId, permits)` — списывает все `permits` разрешений разом, если они есть, иначе ничего не списывает и возвращает `false`;
- `retryAfterNanos(carrierId, permits)` — возвращает `0`, если запрос пройдёт сразу; иначе минимальное число наносекунд, после которого `tryAcquire` гарантированно вернёт `true` (если никто другой не берёт разрешения); `Long.MAX_VALUE`, если запрос больше ёмкости;
- `permits` меньше 1 — `IllegalArgumentException`.

Ведро нового перевозчика заполнено. Запросы приходят из многих потоков.

## Что наблюдается
- После ночи простоя первый пакет заявок утром уходит перевозчику целиком. Перевозчик блокирует маркетплейс за превышение лимита: в ведре оказывается гораздо больше `capacity` разрешений.
- Планировщик повторов ждёт столько, сколько вернул `retryAfterNanos`, но повтор часто снова отклоняется.
- Для слишком больших заявок `retryAfterNanos` возвращает конечное время, и планировщик бесконечно повторяет заявку.

## Что нужно сделать
Исправьте `CarrierBucket` и `CarrierOrderLimiter` по описанию.

## Ограничения
- Конструктор и публичные методы `CarrierOrderLimiter` остаются прежними. `CarrierBucket` можно менять как угодно.
- Запросы разных перевозчиков не должны ждать друг друга на общей блокировке.

## Как будет проверено
Тесты управляют временем через `nanoClock`. Видимые тесты проверяют лимит без простоя. Скрытые тесты проверяют простой, время повтора при разных скоростях, невыполнимые заявки, параллельные запросы после простоя и то, что зависший запрос к одному перевозчику не задерживает запросы к другим.

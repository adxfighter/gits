# Независимое ревью банка задач (P22)

Ревью выполняли агенты, которые не писали варианты, в два круга:
1. **Первый круг** — все 50 вариантов T01–T10 (по два шаблона на ревьюера). Для вариантов уровня junior ревьюер сначала решал задачу «как кандидат» только по `statement.md`, starter и видимым тестам, не открывая `solution/` и скрытые тесты.
2. **Исправления** — по каждому замечанию с оценкой ниже 3 и по большинству существенных замечаний; все изменённые варианты перевалидированы.
3. **Второй круг** — повторное независимое ревью 27 изменённых вариантов. В таблице для них приведены оценки второго круга, для остальных — первого.

Шкала 1–5 по критериям: ясность условия (понятно, что делать, без подсказки решения), реалистичность кода и домена, соответствие уровню и `difficulty_params`, качество скрытых тестов (ловят поверхностные исправления, проверяют только то, что следует из условия, стабильны), уникальность относительно других вариантов шаблона, грамотность русского текста.

**Итог:** вариантов с оценкой ниже 3 нет; все 50 вариантов PASSED после правок; решения кандидатов для 14 вариантов junior проходят скрытые тесты.

## Что изменено после первого круга

Замечания с оценкой ниже 3 (обязательные):
- **T05-v01…v05** — методы starter были в 1,5–5 раз короче шаблона (50–95 строк при заявленных 150–250), дефект в middle/senior виден сразу, в starter были подсказки («ветка скопирована…», комментарий, противоречащий правилу). Все пять вариантов переписаны: методы 150–164 строки с настоящим дублированием, дефект спрятан в одной из копий или во вспомогательном вызове, `difficulty_params` соответствуют коду, скрытые тесты закрепляют все остальные правила (рефакторинг, меняющий поведение, падает). Структура у вариантов разная: цепочка веток по способу доставки, зона × уровень сервиса, цикл по звонкам с шестью блоками, раздельные циклы объёма и стоимости, `switch` с проваливанием.
- **T02-v03** — условие указывало на вспомогательный метод с блокировкой; подсказка удалена.
- **T03-v02** — исправление через FIFO проходило все тесты; добавлен тест, различающий LRU и FIFO.
- **T03-v05** — тест зависел от поведения просроченных записей, которое условие не задаёт; тест и рубрика согласованы с условием, `loc` исправлен.
- **T04-v02** — javadoc readonly-класса и абзац условия раскрывали дефект (тождество ссылок на метод); удалены.
- **T04-v04** — для senior было слишком просто, а условие называло место ошибки; добавлены вложенная тарификация переадресованного плеча (восстановление внешнего контекста) и сохранение исходной ошибки при сбое повторного расчёта, подсказка удалена.
- **T06-v05** — исправление сводилось к удалению поля из `Objects.hash`; добавлено второе расхождение (сравнение трек-номера без учёта регистра), подсказка в javadoc удалена.
- **T08-v03** — скрытый тест требовал обработки синхронного исключения из `score`, не описанной в условии; условие дополнено.
- **T08-v04** — блокирующее исправление (`get(timeout)` в пуле) проходило все тесты; добавлен тест занятости пула, увеличен запас по времени, исправлена фраза условия.
- **T09-v04** — поверхностное исправление («проверить остаток, затем списывать по одному») почти всегда проходило; конкурентный тест использует «уступающие» часы и ловит его стабильно.
- **T10-v05** — эталон бросал «Queue full» при плановой остановке с заполненной очередью; остановка кладёт маркеры через `put`, ёмкость очереди равна `capacity` (исправлено до слияния T10).

## Остающиеся замечания (оценка не ниже 3)

- **Уникальность:** T01-v05 похож на v02 (проверка согласованности снимка), T02-v05 на v04, T03-v02 на v01, T04-v05 — подмножество исправления T04-v04, эталоны T08-v01…v03 и v05 построены по общей схеме «безопасный future на каждый источник».
- **Уровень:** T02-v02, T02-v05, T04-v05, T09-v03 — на нижней границе своего уровня.
- **Подсказки в условиях senior:** T02-v04, T04-v04, T05-v04 довольно явно описывают место проблемы; это следствие правила «скрытые тесты проверяют только то, что сказано в условии».
- **Вероятностные проверки:** частичные исправления T01-v04, T09-v02 (synchronizedMap с get+put) и T10-v02 ловятся с высокой, но не стопроцентной вероятностью. Требования «без глобальной блокировки» в T01, T02 проверяются только рубрикой.
- **Время:** T08-v03, T08-v04, T08-v05 используют таймауты 100–200 мс с запасом 80 мс и более; при сильной перегрузке машины возможен ложный провал эталона. Валидация под нагрузкой (много песочниц одновременно) нестабильна по проверке `reference_time` — валидировать банк нужно одним процессом.
- **Песочница:** примерно в одном прогоне из ста отчёт JUnit не формируется (наблюдалось на T03-v01, T02-v02, T04-v03, T08-v02/v03); повторная валидация проходит. Runner должен повторять такие прогоны (P07).
- **T10-v04:** видимый тест на starter проходит или падает в зависимости от того, успеют ли потребители завершиться до первой отправки.
- **T09-v05:** `threads: 1` в `difficulty_params` при конкурентном тесте на 8 потоков — дефект не многопоточный, конкурентный тест проверяет регрессию.

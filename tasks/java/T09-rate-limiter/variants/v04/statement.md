# Квоты приёма телеметрии

Интеллектуальные счётчики отправляют телеметрию пачками. У каждого устройства (ключ — `deviceId`) есть квота: ведро `DeviceBucket` ёмкостью `capacity`, которое пополняется со скоростью `tokensPerSecond`. Пачка из `n` записей требует `n` разрешений. `TelemetryQuota.tryAcquire(deviceId, permits)` проверяет квоту и создаёт заполненное ведро при первом обращении устройства.

Правила:
- пачка принимается, только если у устройства есть все `permits` разрешений; тогда они списываются разом;
- если разрешений не хватает, пачка отклоняется и **ничего не списывается** — устройство повторит отправку позже;
- пачка больше ёмкости не может быть принята никогда: `false` без списания;
- `permits` меньше 1 — ошибка вызова (`IllegalArgumentException`).

Приём телеметрии многопоточный: пачки одного устройства могут обрабатываться параллельно.

## Что наблюдается
- После первой отклонённой пачки устройство часто не может отправить даже маленькую пачку, хотя по расчётам квота у него есть.
- Под нагрузкой два параллельных запроса одного устройства иногда оба отклоняются, хотя квоты хватило бы на один из них.
- Запрос с `permits = 0` из-за ошибки в прошивке проходит и засоряет журнал.

## Что нужно сделать
Исправьте `DeviceBucket` и `TelemetryQuota` по правилам квоты.

## Ограничения
- Конструкторы и публичные методы `TelemetryQuota` остаются прежними. `DeviceBucket` можно менять как угодно.
- Запросы разных устройств не должны ждать друг друга.

## Как будет проверено
Тесты управляют временем через `nanoClock`. Видимые тесты проверяют пачки, на которые квоты хватает. Скрытые тесты проверяют отклонённые пачки, некорректные значения и параллельные запросы 4 потоков с точным подсчётом принятых пачек и остатка.

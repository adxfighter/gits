# ADR 0005. Загрузка банка задач в БД

**Статус:** принято. **Дата:** 2026-09-27.

## Решения
| Вопрос | Решение | Почему |
|---|---|---|
| Где живёт загрузчик | `TaskBankLoader` в модуле `gits-taskbank`; `gits-api` зависит от `gits-taskbank` как от библиотеки | Чтение банка, проверка контрольной суммы и отчёта уже есть в модуле валидатора — одинаковые правила при валидации и загрузке |
| Артефакты `gits-taskbank` | Исполняемый CLI — `gits-taskbank-exec.jar` (classifier `exec`), обычный `gits-taskbank.jar` — библиотека | Перепакованный Spring Boot jar нельзя подключить зависимостью |
| Когда загружается | При старте api (`ApplicationRunner`), если задан `TASKBANK_PATH` (каталог `tasks/`, смонтирован только для чтения); вручную — `gits-taskbank load tasks/java` | Банк всегда соответствует смонтированным файлам; ручная загрузка — для отладки и администрирования |
| Что загружается | Только варианты с `validation.json` = PASSED и совпадающим `content_hash`, пересчитанным при загрузке | В БД попадает только то, что прошло валидатор без последующих правок |
| Непрошедший вариант | Пропускается с предупреждением; его версия в БД (если есть) остаётся как была. То же для варианта, файлы которого не читаются, и для всех вариантов шаблона без `template.yaml` или с `template.yaml`, не прошедшим схему | Непроверенная или сломанная правка не должна ни попасть к кандидатам, ни отключить проверенную версию |
| Пустой банк | Если в каталоге нет ни одного варианта — ошибка: api не стартует, CLI завершается с кодом 2 | Неверное монтирование не должно отключить весь банк |
| `template.yaml` | Не входит в контрольную сумму варианта; при загрузке проверяется схемой, изменения метаданных шаблона записываются без перевалидации вариантов | Метаданные шаблона не влияют на проверку решения; валидатор тоже проверяет только схему шаблона |
| Идемпотентность | По `code + content_hash`: без изменений — ничего не пишется; изменён — метаданные и файлы заменяются, вариант снова VALIDATED | Повторный старт api не меняет БД |
| Удалённый вариант | Помечается DISABLED, не удаляется | На вариант могут ссылаться сессии и результаты |
| Транзакции | Шаблон + вариант + файлы — одна транзакция на вариант; отключение отсутствующих — отдельная транзакция в конце | Сбой одного варианта не откатывает остальные |
| Образец формата | Шаблон T00 исключается (`gits.taskbank.excluded-templates`, по умолчанию `T00`; у CLI — `--exclude`) | T00 — пример формата, а не задача для кандидатов |
| Компетенции | Коды компетенций хранятся в `task_template.competencies` (jsonb); названия — в `tasks/competencies.yaml` | Отдельная таблица в v1.0 не нужна |

## Следствия и ограничения
- Файлы изменённого варианта заменяются целиком. Сессия, начатая на старой версии, после перезагрузки увидит новые файлы — для v1.0 это допустимо (банк меняется между демонстрациями, не во время сессий). В версии НИОКР — версионирование вариантов или `content_hash` в задании сессии.
- Параллельная загрузка (два экземпляра api или api и CLI одновременно) не блокируется: уникальные ключи не дают испортить данные, но часть вариантов может быть отчитана как пропущенная. В v1.0 api работает в одном экземпляре; при масштабировании — advisory lock PostgreSQL на время загрузки.
- `task_variant.validation_report` хранит отчёт валидатора целиком, в том числе имена скрытых тестов. Как SOLUTION и HIDDEN_TEST, он никогда не отдаётся кандидату (проверяется тестами безопасности API с P07).
- Схема по-прежнему принадлежит `gits-api` (Flyway); CLI `load` только проверяет её (`ddl-auto: validate`) и требует уже созданной БД.
- Через `gits-taskbank` api транзитивно получает `gits-sandbox-client` и библиотеки валидатора. Запуск контейнеров из api не используется, а docker CLI и сокета в контейнере api нет; разделение модулей (отдельный модуль чтения банка) — при необходимости позже.
- Конфигурация логирования CLI называется `logback-taskbank-cli.xml`, а не `logback.xml`, чтобы не подменять логирование api.

# Сканирования посылок теряются

Сортировочные центры отправляют события сканирования посылок в журнал `ScanJournal`. Журнал группирует сканирования по ссылке на посылку `ParcelRef`. Посылку определяют три поля: перевозчик, трек-номер и хаб отправки. Кроме того, в ссылке хранится версия этикетки: если этикетка повреждена, её перепечатывают, и версия увеличивается.

Правила компании:
- перепечатанная этикетка относится к **той же** посылке, поэтому версия этикетки в равенстве не участвует;
- трек-номер сравнивается без учёта регистра: сканеры одних хабов передают его в нижнем регистре, других — в верхнем (`trk-10` и `TRK-10` — одна посылка).

## Что наблюдается
После перепечатки этикетки история посылки распадается на части. Сканирования до и после перепечатки не видны вместе, а число посылок в журнале растёт, хотя новых посылок не было. Похожее происходит, когда посылку сканируют на хабах с разными моделями сканеров: часть истории не находится.

## Что нужно сделать
Исправьте `ParcelRef`, чтобы все сканирования одной посылки собирались вместе независимо от версии этикетки и регистра трек-номера.

## Ограничения
- `ScanJournal` доступен только для чтения.
- Конструктор `ParcelRef(String carrier, String trackingNo, String originHub, int labelVersion)` и методы доступа должны остаться прежними. Версия этикетки по-прежнему доступна через `labelVersion()`.
- Смысл равенства из условия менять нельзя: перевозчик и хаб отправки сравниваются с учётом регистра.

## Как будет проверено
Видимые тесты сканируют посылки без перепечатки и в одном регистре. Скрытые тесты перепечатывают этикетки, передают трек-номер в разном регистре и проверяют контракт `equals`/`hashCode`.

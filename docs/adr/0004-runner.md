# ADR 0004. Исполнитель кода (gits-runner)

**Статус:** принято. **Дата:** 2026-09-27.

## Решения
| Вопрос | Решение | Почему |
|---|---|---|
| Запуск контейнеров | docker CLI (`ProcessBuilder`), а не Docker API-клиент (docker-java) | Передача tar-архива в stdin подключённого контейнера и принудительная остановка по таймауту надёжно работают через CLI на Docker Desktop (Windows) и Linux — это проверено самопроверкой песочницы. У API-клиентов с передачей stdin через HTTP-перехват бывают проблемы. Образ runner содержит docker CLI из `docker:29-cli` |
| Общий код | Модуль `gits-sandbox-client`: параметры запуска, сборка архива, исполнение, разбор протокола, проверка отчёта | Используется runner и валидатором банка задач (P05) — одинаковая изоляция |
| Очередь | Опрос `run_job` каждые 200 мс, `FOR UPDATE SKIP LOCKED`, пул из `RUNNER_CONCURRENCY` потоков; песочница выполняется вне транзакции | Без брокера сообщений; блокировки БД не держатся во время долгого запуска |
| Состав файлов | RUN: редактируемые файлы кандидата + readonly + видимые тесты. SUBMIT: то же + скрытые тесты. SOLUTION не отправляется никогда. Путь из решения, не входящий в редактируемые файлы задачи, — ошибка | Кандидат не может подменить тесты |
| Скрытые тесты | Имена заменяются на «Скрытый тест N», сообщения не сохраняются, консольный вывод SUBMIT не сохраняется, ошибки компиляции SUBMIT показывают только диагностику по файлам кандидата | Условия и код скрытых тестов не раскрываются |
| Подсчёт | RUN — по видимым тестам, SUBMIT — по скрытым | Балл считается по скрытым тестам |
| Восстановление | При старте: удаление контейнеров `gits-run-*`, задания RUNNING → ERROR | В v1.0 один runner; кандидат просто запускает ещё раз |

## Известное ограничение: целостность результатов
Код кандидата выполняется в той же JVM, что и JUnit, поэтому теоретически может подделать XML-отчёт (записать файл и завершить JVM). В v1.0 это затруднено тремя мерами:
1. Статическая проверка файлов кандидата: `System.exit`, `Runtime.halt/exec`, `ProcessBuilder`, `ProcessHandle`, запись файлов, пути песочницы в строках, `setAccessible`, `Unsafe`, внутренние API JDK, загрузка нативного кода.
2. Отчёт сверяется с набором тестов из исходников задачи (`ExpectedTests`): неизвестные классы или отсутствующие методы — отчёт отклоняется.
3. Протокол вывода устойчив к поддельным маркерам (подлинный блок — последний, отчёт в base64).

Полная защита (запуск тестов в отдельном процессе с другими правами, запись отчёта вне досягаемости кода кандидата) запланирована в версии НИОКР.

# Промпты для разработки локальной версии GITS v1.0 (Claude Code)
**Автор:** CTO проекта. **Версия документа:** 1.0. **Назначение:** внутренний документ команды, в заявку не подаётся.
**Цель:** полностью работающая локальная демо-версия платформы GITS для профиля Java-разработчик, запускаемая одной командой `docker compose up` на машине разработчика. Без Yandex Cloud и внешних сервисов.

## 0. Как пользоваться документом
- **Подготовка:** создайте пустой приватный репозиторий `gits` на GitHub, клонируйте его и положите этот документ в `docs/prompts/prompts-v1.0.md`. Промпты ссылаются на его разделы — ничего вставлять вручную не нужно.
- Один промпт — одна задача — одна ветка — один pull request. Промпты выполняются по порядку: каждый следующий опирается на результат предыдущего.
- Перед каждым промптом начинайте новую сессию Claude Code в корне репозитория. Файл CLAUDE.md (промпт P00) подгружается автоматически и задаёт общие правила.
- Для крупных промптов (P03, P07, P10, P14) сначала включите режим планирования, проверьте план, затем разрешите выполнение.
- Каждый промпт заканчивается разделом «Критерии приёмки». Не принимайте результат, пока все пункты не выполнены и проверки не зелёные.
- После каждого промпта выполните промпт ревью R01 (раздел 6), затем commit и pull request на GitHub.
- Блоки промптов P20–P24 (генерация банка задач) выполняются после P05 (валидатор) и до P08 (загрузка в БД). Задачи генерирует Claude в Claude Code на этапе разработки; в работающей системе v1.0 обращений к LLM нет.
|Блок|Промпты|Результат|
|---|---|---|
|Основа|P00–P02|Репозиторий, правила, Docker Compose, схема БД|
|Исполнение кода|P03–P05|Образ песочницы, сервис runner, валидатор банка задач|
|Банк задач|P20–P24|Шаблоны и 50 валидированных вариантов задач для Java-разработчика|
|Backend|P06–P09, P12|Доступ, загрузка задач в БД, сессии оценки, телеметрия, индикаторы и балл|
|Frontend|P10, P11, P13, P14|Интерфейс кандидата, сбор телеметрии, кабинет работодателя, воспроизведение сессии|
|Завершение|P15–P17|Админка и экспорт данных, E2E-тесты и демо-данные, выпуск v1.0|

## 1. Архитектурные решения v1.0
|Решение|Выбор|Обоснование|
|---|---|---|
|Репозиторий|Монорепозиторий `gits` на GitHub (приватный)|ИИ-ассистент видит весь контекст; одна команда запуска; один CI|
|База данных|PostgreSQL 17|JSONB для телеметрии, очередь заданий на `SELECT … FOR UPDATE SKIP LOCKED`, Flyway-миграции|
|Redis|**Не используется в v1.0**|Очередь запусков — в PostgreSQL, сессии — cookie на одном экземпляре API. Redis добавим при горизонтальном масштабировании|
|Backend|Java 21, Spring Boot 3.5, Maven, модульный монолит|Соответствует заявке и компетенциям команды|
|Модули Maven|`gits-core` (домен, JPA), `gits-api` (REST, Flyway), `gits-runner` (исполнитель), `gits-taskbank` (CLI валидатора и загрузчик)|Доступ к Docker-сокету есть только у runner|
|Frontend|Angular 21 (standalone, signals), Monaco Editor из локальных ассетов, nginx|Нет зависимостей от CDN: демо работает без интернета|
|Песочница|Отдельный образ `gits-sandbox-java`: JDK 21, JUnit 5, AssertJ, Mockito|Каждый запуск — новый контейнер: без сети, с лимитами, только для чтения, tmpfs|
|Изоляция|runc по умолчанию; runsc (gVisor) — через переменную `SANDBOX_RUNTIME` на Linux|Docker Desktop под Windows не поддерживает gVisor штатно|
|Передача кода в песочницу|tar-архив через stdin контейнера, распаковка в tmpfs `/work`|Не нужны bind mount путей хоста (проблема Windows)|
|Взаимодействие фронта с API|REST, опрос результата запуска раз в секунду; телеметрия — пакетами по HTTP раз в 2 секунды|Проще и надёжнее WebSocket для демо|
|Аутентификация|Работодатель — email и пароль (BCrypt), сессионная cookie и CSRF. Кандидат — одноразовая ссылка-приглашение|Минимум сложности для демо|
|LLM в runtime|Нет. Интерфейс `LlmClient` и заглушка `StaticPoolTaskProvider`; банк задач сгенерирован заранее|Демо без ключей и внешних API; YandexGPT и GigaChat подключаются в версии гранта|
|Профиль и объём задач|Java-разработчик (Java 21 core, без Spring в v1.0), 10 шаблонов × 5 вариантов = 50|Spring-задачи — в v1.1: тяжёлый старт контекста в песочнице|
|Язык|Код и идентификаторы — английский; интерфейс, условия задач и документация — русский|—|

```
Ты — ведущий разработчик проекта GITS. Создай каркас монорепозитория локальной демо-версии v1.0.

Контекст: GITS — платформа оценки практических навыков Java-разработчиков. Ограничения: никаких облачных SDK; никаких секретов в репозитории; Redis не добавлять.

Критерии приёмки:
- `scripts/up.ps1` на Windows и `scripts/up.sh` на Linux поднимают все сервисы, `docker compose ps` — все healthy.
```

**Текст CLAUDE.md (используется промптом P00):**
```
# GITS — правила проекта

## Что это
Локальная демо-версия v1.0 платформы оценки практических навыков Java-разработчиков.
Запуск: scripts/up.ps1 (Windows) или scripts/up.sh (Linux/macOS). UI: http://localhost:8080.

## Стек
Backend: Java 21, Spring Boot 3.5, Maven, PostgreSQL 17, Flyway, Spring Data JPA, Testcontainers.
Frontend: Angular 21 (standalone, signals), Monaco Editor (локальные ассеты), SCSS.
Песочница: образ gits-sandbox-java (JDK 21, JUnit 5, AssertJ, Mockito).

## Модули и границы
- gits-core: доменные сущности, репозитории, общие DTO. Не зависит от web.
- gits-api: REST-контроллеры, безопасность, Flyway-миграции (единственный владелец схемы БД).
- gits-runner: исполнитель кода. Единственный модуль с доступом к Docker. Не имеет REST API.
- gits-taskbank: CLI валидатора банка задач и загрузчик задач в БД.
- frontend не содержит бизнес-логики оценки; всё считается на backend.

## Жёсткие правила безопасности
- Скрытые тесты и эталонные решения никогда не отдаются через API кандидату. Любой новый endpoint, возвращающий задачу, должен иметь тест, проверяющий отсутствие этих данных.
- Контейнер песочницы: --network=none, read-only rootfs, tmpfs /work, лимиты памяти/CPU/pids, непривилегированный пользователь, таймаут, удаление после запуска. Не ослаблять без ADR.
- Никаких секретов в коде и тестах; только через .env. Пароли — BCrypt.
- Телеметрия собирается только после согласия кандидата и только внутри страницы оценки. Символы нажатых клавиш не логируются — только категория клавиши.

## Стиль
- Код, идентификаторы, коммиты — на английском. Интерфейс, условия задач, документация — на русском.
- Backend: конструкторная инъекция, record для DTO, без Lombok, ошибки — Problem Details (RFC 9457).
- Frontend: standalone-компоненты, signals для состояния, строгая типизация, без any.
- Каждое изменение сопровождается тестами. Интеграционные тесты БД — Testcontainers.

## Проверка перед завершением задачи
1. cd backend && mvn -q verify
2. cd frontend && npm run lint && npm test && npm run build
3. docker compose up --build -d и ручная проверка изменённого сценария
Не сообщай, что задача выполнена, если какая-то проверка не прошла.

## Архитектурные решения
docs/adr/. Новое существенное решение — новый ADR.
```

## 3. Промпты P01–P05. Основа и исполнение кода
### P01. Схема базы данных
```
Спроектируй и реализуй схему БД GITS v1.0 во Flyway-миграциях (gits-api/src/main/resources/db/migration) и JPA-сущности в gits-core.

Сущности (уточни поля и индексы сам, обоснуй в docs/adr/0002-db-schema.md):
- company, app_user (роли EMPLOYER, ADMIN; email уникален; password_hash).
- task_template (код T01..T10, название, компетенции, базовый уровень, параметры модели сложности JSONB).
- task_variant (код T01-v03, template_id, уровень junior/middle/senior, difficulty_params JSONB, statement_md, time_limit_min, content_hash, status VALIDATED/DISABLED, validation_report JSONB).
- task_file (variant_id, kind STARTER/SOLUTION/VISIBLE_TEST/HIDDEN_TEST/READONLY, path, content, editable).
- invite (company_id, created_by, candidate_label, target_level, token_hash, expires_at, status CREATED/STARTED/COMPLETED/EXPIRED).
- consent (invite_id, version, accepted_at, ip_hash, user_agent).
- assessment_session (invite_id, started_at, finished_at, time_limit_min, status, random_seed).
- session_task (session_id, variant_id, order_no, kind CALIBRATION/TASK, started_at, submitted_at, current_code JSONB — снимок редактируемых файлов).
- run_job (session_task_id, mode RUN/SUBMIT, status QUEUED/RUNNING/DONE/ERROR/TIMEOUT, payload JSONB, created_at, started_at, finished_at, worker_id) + индекс под выборку очереди.
- run_result (run_job_id, compiled bool, compile_output text, tests_total, tests_passed, test_cases JSONB, duration_ms, stdout_trunc, stderr_trunc).
- telemetry_batch (session_task_id, seq, client_ts_start, client_ts_end, received_at, events JSONB), уникальность (session_task_id, seq).
- session_indicators (session_task_id, indicators JSONB, trust_level GREEN/YELLOW/RED, computed_at).
- session_score (session_id, per_task JSONB, preliminary_score numeric, computed_at).
- audit_log (actor, action, entity, entity_id, at, details JSONB).

Требования: UUID первичные ключи, timestamptz, внешние ключи с ON DELETE, где уместно; токен приглашения хранится только как хэш (SHA-256).

Критерии приёмки:
- Миграции применяются на чистой БД при старте api.
- Интеграционный тест (Testcontainers) создаёт по одной записи каждой сущности и читает обратно.
- Тест проверяет, что выборка очереди `FOR UPDATE SKIP LOCKED` двумя параллельными транзакциями не берёт одно задание дважды.
```

### P02. Доступ: работодатель, приглашения, согласие
```
Реализуй аутентификацию и авторизацию GITS v1.0 в gits-api.

1. Работодатель: вход по email и паролю (Spring Security, form login через REST: POST /api/auth/login, POST /api/auth/logout, GET /api/auth/me), сессионная cookie HttpOnly+SameSite=Lax, CSRF (cookie XSRF-TOKEN для Angular).
2. При старте api создаётся демо-компания и пользователь-работодатель из переменных DEMO_EMPLOYER_EMAIL и DEMO_EMPLOYER_PASSWORD, а также ADMIN из DEMO_ADMIN_EMAIL/DEMO_ADMIN_PASSWORD (если заданы). Идемпотентно.
3. Приглашения: POST /api/invites (EMPLOYER) — candidate_label, target_level (JUNIOR/MIDDLE/SENIOR); ответ содержит одноразовую ссылку http://localhost:8080/c/{token} (токен 32 байта, в БД — только хэш, срок 7 дней). GET /api/invites — список приглашений компании со статусами.
4. Кандидат: POST /api/candidate/enter {token} → создаёт кандидатскую сессию (отдельная cookie с ролью CANDIDATE, привязанной к invite_id). Повторный вход по тому же токену после завершения оценки запрещён.
5. Согласие: GET /api/candidate/consent — текст согласия (версия 1, текст положи в resources/consent/v1.md, возьми за основу абзац «Текст согласия» ниже), POST /api/candidate/consent — фиксирует согласие. Без согласия все кандидатские endpoint'ы, кроме consent, возвращают 403.
6. Ограничение частоты: вход работодателя — 10 попыток в минуту на IP; вход по токену — 20 в минуту на IP.

Текст согласия (основа): платформа собирает временные характеристики нажатий клавиш (без самих символов), изменения кода в редакторе, события вставки и переключения вкладки, результаты запусков тестов; цель — оценка навыков и достоверности сессии; хранение локально на сервере демо-версии; видео, аудио и снимки экрана не собираются; согласие можно отозвать.

Критерии приёмки:
- Интеграционные тесты: успешный и неуспешный вход; доступ к /api/invites без роли — 401/403; кандидат без согласия — 403; повторное использование токена после завершения — 410.
- Пароли и токены не появляются в логах (тест на логирование через OutputCaptureExtension).
```

### P03. Образ песочницы для Java
```
Создай образ песочницы sandbox/java для исполнения кода кандидатов.

Требования к образу gits-sandbox-java:
- База eclipse-temurin:21-jdk (alpine, если всё работает), пользователь sandbox с uid 10001.
- В /opt/libs: junit-platform-console-standalone (актуальная 1.x для JUnit 5), assertj-core, mockito-core и её зависимости (byte-buddy, objenesis). Версии зафиксированы, скачиваются на этапе сборки образа, проверяется SHA-256.
- /opt/gits/entrypoint.sh:
  1) читает tar-архив из stdin и распаковывает в /work/src (tmpfs);
  2) компилирует все .java из /work/src/main и /work/src/test в /work/out (javac --release 21, -encoding UTF-8, classpath /opt/libs);
  3) при ошибке компиляции печатает маркер ===GITS-COMPILE-ERROR=== и вывод javac, код выхода 2;
  4) запускает JUnit Console Launcher (execute, --scan-class-path /work/out, отчёт в /work/reports), JVM-флаги -Xmx384m -XX:+UseSerialGC -XX:TieredStopAtLevel=1 -Xss512k;
  5) печатает маркеры ===GITS-REPORT-BEGIN===, содержимое XML-отчёта JUnit, ===GITS-REPORT-END===.
- Вывод stdout/stderr теста ограничен 64 КБ.

Параметры запуска (их будет применять runner, задокументируй в sandbox/java/README.md):
--network=none --read-only --tmpfs /work:rw,size=64m,exec --tmpfs /tmp:rw,size=16m --memory=768m --memory-swap=768m --cpus=1 --pids-limit=128 --cap-drop=ALL --security-opt=no-new-privileges --user 10001 -i (stdin), таймаут 30 секунд на стороне runner, --runtime из SANDBOX_RUNTIME.

Добавь sandbox/java/selftest/: набор «злых» программ и скрипт scripts/sandbox-selftest.(sh|ps1), который проверяет:
- сетевой запрос (HttpClient к 1.1.1.1) — падает;
- бесконечный цикл — завершается по таймауту;
- fork-бомба (массовое создание потоков/процессов) — упирается в pids-limit, хост не страдает;
- выделение 2 ГБ памяти — OOM внутри контейнера;
- запись в / и /opt — запрещена;
- чтение /etc/passwd возможно, но секретов хоста в контейнере нет (переменные окружения пусты, кроме необходимых);
- корректная программа с тестами — отчёт JUnit выводится между маркерами.

Критерии приёмки: selftest проходит на Windows (Docker Desktop) и Linux; запуск простой задачи с 5 тестами — не более 4 секунд на тёплой машине.
```

### P04. Сервис runner
```
Реализуй модуль gits-runner — фоновый сервис исполнения кода кандидатов (Spring Boot без web-сервера, spring.main.web-application-type=none).

1. Опрос очереди: каждые 200 мс берёт до RUNNER_CONCURRENCY заданий run_job в статусе QUEUED через SELECT … FOR UPDATE SKIP LOCKED, помечает RUNNING, worker_id = hostname.
2. Сборка архива: для mode=RUN — редактируемые файлы кандидата (из payload) + READONLY файлы варианта + VISIBLE_TEST; для mode=SUBMIT — то же + HIDDEN_TEST. Файлы SOLUTION никогда не включаются. Пути нормализуются, запрет «..» и абсолютных путей, лимит 256 КБ на архив, 50 файлов.
3. Запуск контейнера через docker-java (транспорт httpclient5, сокет unix:///var/run/docker.sock) с параметрами из sandbox/java/README.md; tar передаётся через stdin (attach). Таймаут 30 с: по истечении — kill, статус TIMEOUT.
```

### P12. Индикаторы достоверности и предварительный балл
```
Реализуй расчёт индикаторов и балла в gits-api (сервис IndicatorService, ScoreService), запускается после finish и доступен для пересчёта админом.

Индикаторы по каждой задаче (все — с русским пояснением и порогами в конфигурации):
- pasteRatio — доля символов, пришедших вставкой, от итогового объёма редактируемого кода; largestPaste — наибольшая вставка;
- focusLoss — число и суммарная длительность потери фокуса/скрытия вкладки;
- burstMax — максимальная скорость ввода (символов в секунду) в скользящем окне 5 с, без учёта вставок и автодополнения;
- idleThenBurst — число эпизодов «пауза > 30 с, затем > 150 символов за < 20 с без вставки»;
- linearity — доля правок в конце документа (набор «сверху вниз» без возвратов) от всех правок;
- editRatio — удалённые символы / вставленные символы;
- timeToFirstRun, runsCount.
trust_level: GREEN / YELLOW / RED по правилам (например, RED: pasteRatio > 0,5 или idleThenBurst ≥ 2 при focusLoss > 60 с); правила — в application.yml, документированы в docs/indicators.md с пометкой «экспериментальные правила v1.0; в версии НИОКР заменяются моделями машинного обучения».
Калибровочный блок: индикаторы считаются, но в trust_level не входят; сохраняется базовая скорость набора кандидата — burstMax оценивается относительно неё.
Балл: по задаче — доля пройденных скрытых тестов; веса уровня junior 1, middle 1,5, senior 2; preliminary_score 0–100 — взвешенное среднее; помечается как «предварительный, до психометрической калибровки».
Критерии приёмки: unit-тесты на синтетических потоках событий для каждого индикатора (честный набор, крупная вставка, пауза и всплеск, линейный перенос); отчёт работодателя показывает индикаторы.
```
